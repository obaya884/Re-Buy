# FavBasket ロードマップ

- 作成日: 2026-08-29
- 更新日: 2026-08-29
- ステータス: 確定（①に着手）
- 位置づけ: プロジェクト全体を 5 つのサブプロジェクトに分け、その順序と各々の範囲・完了条件を定める。各サブプロジェクトは着手時に個別にブレストし、仕様（spec）→ 実装計画 → 実装の通常サイクルで進める。本書は各サブプロジェクトの完了時に更新する
- 置き場所: ②（開発基盤）で docs/ の番号付き構造を決めた時点で、その体系に組み込む

## 1. ゴール

オーナーが挙げた 5 つの到達点。

1. KMP 対応（マルチプラットフォーム）とマルチモジュール化
2. プロジェクト憲章などの作成
3. 憲章に沿ったユーザー体験・機能の見直し
4. [obaya884/hitosuji](https://github.com/obaya884/hitosuji) 並みの AI 主導開発体制
5. App Store・Google Play へのリリースと、収益化を目標にしたグロース

## 2. 前提

- **プロダクト**: 「くりかえし使える買い物リスト」。アイテムを使い捨てにせず、買い物のたびにカゴへ入れ → 店でチェック → 終了でプールに戻す（最終購入日付き）。基本ループ（ホーム → カゴ → 買い物 → 終了）は実装済みだが、オーナー自身が日常利用できる状態ではない（作りかけ）
- **ペース**: 2023-03 開始、趣味ペース。計画は日付ではなく順序で管理する
- **KMP の動機**: iOS ユーザーへの到達だけでなく、**KMP を学ぶこと自体が目的の一つ**。コードが小さい（約 45 ファイル）今のうちに構造を変えるのが最も安い
- **hitosuji から持ち込む考え方**: 仕様（docs/）が正でコードは従う／台帳で「次」を決める／役割分担した AI（レビュアー・検証係）／機械で守る（docs-check・CI）。ただし hitosuji は web・シングルユーザー・実運用中の前提で組まれているため、丸写しではなく Android＋公開プロダクト向けに翻訳し、**段階的に採用**する

## 3. 順序

```
① 憲章 → ② 開発基盤 → ③ KMP＋マルチモジュール → ④ 機能・UX 見直し → ⑤ リリース・グロース
                          （挙動を変えない移植）      （docs → 新構造の上で実装 → 自分で使う）
```

## 4. 各サブプロジェクト

### ① プロジェクト憲章

- **目的**: 以降すべての判断基準を 1 文書にする。hitosuji の `11_要求定義書` §1〜5 に相当
- **決めること**: 誰のため（オーナー自身＋公開ユーザー）／解く問題／重視する価値／成功基準／スコープ外／収益モデルの仮説／対象プラットフォーム
- **成果物**: 憲章文書。要求一覧（F-XXX）はここでは作らず ④ で作る
- **完了条件**: オーナーが「これがあれば迷わない」と言える
- **進め方**: 対話で書く。コードなし。文書そのものが成果物なので実装計画は作らない

### ② 開発基盤（hitosuji の翻訳。骨格だけ）

- **入れるもの**: docs/ の構造と番号規約／CLAUDE.md の全面改訂（技術メモから運用ガイドへ）／agents 4 本（verifier・code-quality-reviewer・spec-reviewer・test-reviewer を Android 向けに）／`.claude/settings.json` の権限／`docs-check.sh` の移植／CI（build・lint・unit test）／ブランチ運用の決定／台帳 22（要件バックログ）・23（技術改善）を空で用意
- **完了条件**: CI 緑、docs-check が CI で走る、③ の最初の PR でレビュアーが 1 回実戦で回る
- **リスク**: 作りすぎ。hitosuji の仕組みは運用 1 か月半で育ったもの。最初は骨格に留め、必要が出た時点で足す

### ③ KMP 化＋マルチモジュール化（挙動を変えない移植）

- **範囲**: 既存の Item / Category / 3 状態 / 全画面を新構造へ載せ替える。Android の見た目・動作は変えない。学習の主戦場
- **spec で決めること**: モジュール境界／DI（Hilt は KMP 非対応。Koin または Metro）／Room KMP の iOS 側ドライバ／Navigation／iOS プロジェクトの持ち方／commonTest の範囲／CI に iOS ビルドを足すか（macOS ランナー）／何を学ぶかの明示
- **完了条件**: Android が移植前と同一挙動、iOS シミュレータで同じ画面が動く、テストが commonTest で通る、CI 緑
- ここが ② の体制で回す最初の実戦になる

### ④ 機能・UX 見直し → MVP 実装 → 自分で使う

- **範囲**: 憲章に照らして要件定義・画面定義・データモデル定義を書き、F-XXX を起こし、MVP を決め、1 F = 1 ブランチ = 1 PR の通常フローで実装する。オーナーの端末に入れて使い始める。**FB 台帳（21）と `next-task` はここで開始**
- **完了条件**: MVP の F-XXX がすべて closed、オーナーが数週間使い続けている、FB が回っている

### ⑤ リリース・グロース

- **範囲**: Play Console／App Store Connect、署名とリリースパイプライン（内部テスト・TestFlight）、利用規約・プライバシーポリシー、計測、クラッシュレポート、課金（モデルは ①）、ASO、台帳に「監視項目」レーンを追加
- **完了条件**: 両ストア公開、収益が計測できる、グロース施策が台帳で回る
- **要確認の外部制約**: Apple Developer Program（年額）／Play の個人開発者アカウントは製品版公開前にクローズドテスト（十数人 × 14 日）が必須。既存の Play アカウントの有無で重さが変わる

## 5. hitosuji の仕組みを入れる段階

| 段階 | 入れるもの |
|---|---|
| ② | docs 構造・CLAUDE.md・レビュアー 4 本・docs-check・CI・台帳 22/23・ブランチ運用 |
| ④ | FB 台帳 21 と guide・`next-task` スキル |
| ⑤ | 監視項目レーン・`dependabot-triage`・リリース用スクリプト |
| 必要になったら | worktree 並行開発（ヘッド＋ワーカー）・browser-checker 相当（エミュレータ＋`android` CLI） |

## 6. 進め方の原則

- **各サブプロジェクトが単独で価値を残す**。途中で止まっても、リポジトリはその時点で前より良い状態になっている
- 各サブプロジェクトは brainstorming → spec → plan → 実装の通常サイクルで回す（① を除く）
- 挙動レベルの仕様判断はオーナーとの対話でのみ決める（hitosuji と同じ）

## 7. 今は決めないこと

収益モデル（①）／モジュール構成と DI（③）／MVP の範囲（④）／計測基盤（⑤）／docs 番号体系の細部（②）

## 8. 決定ログ

| 日付 | 決定 | 理由 |
|---|---|---|
| 2026-08-29 | 憲章を先頭に置く | 「iOS が要るか」「バックエンドが要るか」「何を収益化するか」がすべて憲章で決まり、KMP の構造にも影響するため |
| 2026-08-29 | KMP を機能見直しより前に置く | KMP を学ぶこと自体が目的の一つであり、コードが約 45 ファイルの今が移植コスト最小。④ の新機能は最初から KMP 側に書けばよい |
| 2026-08-29 | ③ を「挙動を変えない移植」に限定する | 移植と機能追加を混ぜると、壊れたときにどちらが原因か切り分けられないため |

| 2026-08-29 | hitosuji の仕組みは段階的に採用する | hitosuji は実運用中の web アプリの前提で組まれており、未リリースの Android アプリに丸ごと入れても回らない。FB 台帳は実利用が始まってから、監視項目はリリース後 |
