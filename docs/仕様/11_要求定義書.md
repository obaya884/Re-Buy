## 1. 背景

世に多くある買い物リストアプリは、**品目を追加し、店でチェックし、削除する**という単発型が大半である。しかし日常の買い物——とくにスーパーや薬局——で買うものは、毎回ほとんど同じ品目である。単発型のリストでは、同じ品目を毎回入力し直すことになり、その手間がリストを使う気を削ぐ。

もう一つ、一人暮らしの社会人には、買い物を含む家事を後回しにしがちだという事情がある。「何を買うか」「どこへ行くか」を考えるところから始めると腰が重い。逆に、**やることも行く場所も決まっている**状態が先にできていれば、あとは出かけるだけになる。

本プロジェクトのオーナーは、この 2 つを自分の問題として持っており、既存のアプリではどちらも解決しなかった。2023 年に自分で作り始め、動機は 2026 年の時点でも変わっていない。

## 2. 目的

くりかえし買うものを一度登録すれば、以後は入力なしで買い物に出かけられるリストを手に入れる。それによって、買い物という家事の腰を軽くする。

### 2.1 成功基準

次の 2 つが両方満たされたとき、本プロジェクトは成功したと言う。

1. **オーナー自身が毎週の買い物で使い続けている**（他のメモ手段に戻らない）
2. **App Store と Google Play の両方で公開され、オーナー以外の人が使っている**

収益化は目標であり、グロースの活動は ⑤ で行うが、**収益の有無は成功の必要条件にしない**。KMP と AI 主導開発の習得はプロジェクトの動機の一つだが、成果物ではなく副産物として扱う。

## 3. 対象ユーザーと利用シーン

- **対象ユーザー**: 自分の分の買い物を自分でする人。典型は一人暮らしの社会人。オーナー自身がその一人であり、最初のユーザーでもある
- **共有しない**: 家族やパートナーとリストを共有する世帯は対象にしない（§7）。リストは一人のものとして設計する
- **利用シーン**:
  - 平時: 切れそうなもの・欲しいものに気づいたとき、登録済みの品目をカゴへ入れる（数秒の操作）
  - 出発前: カゴの中身を見て「今日はこれを買いに行く」と決める
  - 店で: カゴの品目を見ながら棚を回り、取ったものにチェックを入れる
  - 会計後: 「買い物を終わる」でチェック済みの品目をプールに戻す。次回はまたカゴへ入れるだけ
- **利用環境**: スマートフォン（Android / iOS）。店内で片手で使う。通信がなくても動くこと
- **市場・言語**: 初回リリースは日本市場・日本語のみ。英語対応は将来の候補（§7）

## 4. コンセプトと用語: くりかえし使える買い物リスト

品目を使い捨てにしない。品目は**プール**に常駐し、買い物のたびに**カゴ**を経由してプールへ戻る。要求（§6）はすべてこのループの上に立つ。

```
プール（登録済みの品目）──カゴへ入れる──▶ カゴ（今日買うもの）──店でチェック──▶ チェック済み
   ▲                                                                              │
   └───────────────────────── 「買い物を終わる」でプールへ戻る（最終購入日を記録）──┘
```

### 4.1 品目の 3 つの状態

品目は常にプールにあり、次の 3 つの状態のどれか 1 つを取る。**利用者が削除しない限り、どの状態でも品目は消えない**。

| 状態 | 意味 | 次に起きること |
|---|---|---|
| 常駐 | 今回は買わない。プールにいるだけ | 必要になったらカゴへ入れる |
| カゴ入り | 今日買うものとして選ばれている | 店でチェックするか、気が変われば出す |
| チェック済み | 店で取った | 「買い物を終了する」で最終購入日を記録して常駐へ戻る |

### 4.2 用語

本書と下位文書は次の語を同じ意味で使う。UI に出す言い回しは別に決めている（[画面定義書](./13_画面定義書.md) §3。たとえば利用者には「プール」「カゴ」という語を見せない）。

| 用語 | 意味 |
|---|---|
| 品目 | 買うものの 1 つ。名前を持ち、カテゴリと行き先を 0〜1 個ずつ持てる |
| プール | 登録済みの全品目の集合。買い物リストの「台帳」に当たる。品目は削除されるまでここに居続ける |
| カゴ | 今日買うものとして選ばれた品目の集合。独立した入れ物ではなく、プールの品目の状態（カゴ入り・チェック済み）として表す |
| チェック | 店で取った品目に付ける印。買い物を終了するまで何度でも付け外しできる |
| 買い物（買い物モード） | 行き先を 1 つ選んで店内でチェックして回る一連の操作。終了でカゴが片づく |
| 最終購入日 | 品目を最後にチェック済みで終了した日。「前に買ったのはいつか」を表す |
| カテゴリ | 品目の区別タグ（食料品・生活用品のような）。並び順を手で決められる |
| 行き先 | 品目を買う店。カテゴリとは独立の軸で、買い物を始めるときの単位になる。並び順を手で決められる |
| どこでも買えるもの | 行き先を持たない品目。どの行き先の買い物にも一緒に入る |
| 全件モード | カゴに行き先付きの品目が 1 つも無いときの買い物。行き先を選ばず、カゴ全件を 1 つの一覧でチェックする |

カテゴリと行き先が別の概念である理由は[決定ログ](./log_11_要求定義書.md) 2026-08-31。

## 5. 重視する価値

機能の要否や優先度で迷ったとき、次の順で判断する。番号は要件定義書ほか各文書からの参照用。

| ID | 価値 | 意味 |
|---|---|---|
| C-1 | **繰り返しの入力をゼロに近づける** | 一度登録した品目は二度と打たない。カゴへ入れる・チェックする・戻す、の操作だけで回る |
| C-2 | **腰を軽くする** | 起動から「買い物に行く」までが最短。「何を買うか」「どこへ行くか」を考えなくて済む状態を先に作る。この価値は C-1 の帰結ではなく、独立した目的として扱う |
| C-3 | **端末内で完結する** | アカウントなし、サーバーなし、オフラインで動く。データは端末の中にあり、外へ出ない |
| C-4 | **単純さ** | 機能を足すより、基本ループの速さと分かりやすさを守る。迷ったら足さない |
| C-5 | **両 OS で同じ体験** | Android と iOS で機能を揃える。片方だけの機能を作らない。揃えるのは「何ができるか」であって見た目ではなく、画面の作法は各 OS の慣習に合わせる |

価値が衝突したら小さい番号を優先する。ただし C-3 は前提であり、C-1・C-2 のために C-3 を崩す（サーバーを持つ）ことはしない。

## 6. 要求

製品が何をできるか（機能要求 F-XXX。§6.1〜§6.5）と、どの機能にも掛かる品質と制約（非機能要求 N-XX。§6.6）の全体。**この表が製品の地図**で、実装済みのものも将来のものも同じ表に載せる。要求の実現方針は[要件定義書](./12_要件定義書.md) §5、未実装の要求の状態と着手トリガは[要件バックログ](../案件/22_要件バックログ.md)が持つ。

- **番号**: 百の位が領域を表す（1xx 品目とプール／2xx カゴと買い物／3xx カテゴリと行き先／4xx 設定と見た目／5xx 収益）。領域の中は起こした順で、並び替えない。**F-001〜F-013 は ④ の MVP で作業単位に使った番号**で、[完了記録](../案件/closed_22_要件バックログ.md)にそのまま残し、再利用しない（対応は[決定ログ](./log_11_要求定義書.md) 2026-10-05）
- **優先度**: **Must**（ないと日常の買い物が成立しない。④ の MVP ですべて実装済み）／ **Should**（⑤ のストア公開までに要る）／ **Could**（将来の候補。やるかどうかは台帳で見極める）。やらないと決めたものは表から外して §7 スコープ外へ落とす
- **挙動が増える・変わるとき**は、FB・技術改善のどちらから出たものでも、**先にここの行を足すか文を直す**（運用は [FB 台帳](../案件/21_FB台帳.md)の運用ルール）。要求に無い挙動を下位文書だけで決めない

### 6.1 品目とプール

| ID | 要求 | 優先度 |
|---|---|---|
| F-101 | 品目は一度登録すればプールに常駐し、買っても消えない。買い物のたびにカゴを経由してプールへ戻る（§4 の基本ループ。C-1） | Must |
| F-102 | 名前を打つだけの最短操作で品目を登録でき、同じ場で続けて次を登録できる | Must |
| F-103 | 品目にカテゴリ（区別タグ）を 0〜1 個付けられる | Must |
| F-104 | 品目にカテゴリとは独立の行き先（買う店）を 0〜1 個付けられる。行き先のない品目は「どこでも買えるもの」として扱う（C-2） | Must |
| F-105 | 品目の名前・カテゴリ・行き先を後から直せ、品目を削除できる | Must |
| F-106 | 品目・カテゴリ・行き先の名前は検証され、空・同種内の重複・長すぎる名前は登録できない | Must |
| F-107 | 全品目を 1 画面で一覧でき、カテゴリと行き先で絞り込める | Must |
| F-108 | 品目は最終購入日を持ち、一覧で「前に買ったのはいつか」が分かる | Must |
| F-109 | プールの長押しで開く操作（品目の編集）に、初見でも気づける手がかりを持つ | Could |

### 6.2 カゴと買い物

| ID | 要求 | 優先度 |
|---|---|---|
| F-201 | プールの行を 1 タップでカゴに入れる・出せる。プールでカゴの件数が見える | Must |
| F-202 | 出発前にカゴの中身を行き先別に確かめ、行き先を選んで買い物を始められる。行き先付きの品目がカゴに無ければ、選ぶ段を挟まずに始まる（C-2） | Must |
| F-203 | 店内で、選んだ行き先の品目とどこでも買えるものを 1 つの一覧で見ながら、取ったものにチェックを付け外しできる | Must |
| F-204 | 「買い物を終了する」で、チェック済みの品目だけが最終購入日付きでプールへ戻る。未チェックはカゴに残る | Must |
| F-205 | 買い物の途中で気づいたものを、その場で探してカゴに足せる。他の行き先のものはその行き先のカゴへ入り、まだ無いものはその場で登録できる | Must |
| F-206 | 買い物を途中でやめても、チェックした内容は残り、あとから続きを再開できる | Must |
| F-207 | 品目が増えても、気づいたものの検索で目的の品目をすぐ見つけられる（当たりが増えても埋もれない） | Could |

### 6.3 カテゴリと行き先

| ID | 要求 | 優先度 |
|---|---|---|
| F-301 | カテゴリを一覧・並び替え・追加・名前変更・削除できる | Must |
| F-302 | 行き先を一覧・並び替え・追加・名前変更・削除できる | Must |
| F-303 | カテゴリ・行き先は、品目の登録・編集の途中でもその場で作って選べる | Must |
| F-304 | カテゴリ・行き先を削除しても、紐づく品目は消えない（カテゴリなし／どこでも買えるものになる）。影響する件数が削除前に分かる | Must |

### 6.4 設定と見た目

| ID | 要求 | 優先度 |
|---|---|---|
| F-401 | 配色テーマを 3 案（若葉・藍・柿）から選べる。既定は藍、明暗は OS 設定に追従する | Must |
| F-402 | 設定から、カテゴリ・行き先の管理、テーマ、同梱 OSS のライセンス、アプリのバージョンに到達できる | Must |
| F-403 | 利用規約・プライバシーポリシー・問い合わせ先に設定から到達できる（ストア公開の条件。それまでは導線を出さない） | Should |

### 6.5 収益

§8 の仮説を要求として置いたもの。初回リリースには入れず、ユーザーがついてから ⑤ で導入する。

| ID | 要求 | 優先度 |
|---|---|---|
| F-501 | 広告を表示する。店内で使う画面（買い物・気づいたものを足す）の邪魔をしない | Could |
| F-502 | プレミアム（広告非表示を含む）を購入できる。基本ループは有料化しない（C-4） | Could |

### 6.6 非機能

どの機能にも掛かる品質と制約。**ここに書くのは「何が成り立っていなければならないか」だけ**で、どう実現するか（手段・数値・網）は[要件定義書](./12_要件定義書.md) §5.6 とその参照先が持つ。優先度は付けない——どれも満たしていなければ出せない。

| ID・区分 | 要求 |
|---|---|
| `N-01` データ保全 | アプリを更新しても、利用者のデータを黙って失わない。移行できないときは消して続けず、起動時に落ちて気づけるほうを採る |
| `N-02` データ保全 | 買い物の途中でアプリを離れても、OS にプロセスを落とされても、続きから再開できる |
| `N-03` プライバシー | 利用者が登録したデータは端末の外へ出ない。アカウントもサーバーも持たず、通信がなくても全機能が動く。**OS のバックアップ（Android の Auto Backup・iOS の iCloud バックアップ）に入るのは例外**で、利用者が OS 側で選ぶものとして認める |
| `N-04` 対応環境 | スマートフォンで動く。最低 OS バージョンは §9。iOS は iPhone のみで、タブレットに合わせたレイアウトは持たない |
| `N-05` アクセシビリティ | 選択の状態を色だけで示さない。色に頼らない手がかりを 1 つ持たせる |
| `N-06` アクセシビリティ | 選択を示す面の上でも、基本の文字は WCAG AA（4.5:1）を割らない |
| `N-07` 言語 | 表示は日本語のみ。文言はリソースに置き、言語を足せる形を保つ |
| `N-08` ライセンス | 同梱する OSS のライセンスをアプリ内で表示し、依存の増減に表示が追随する |
| `N-09` 公開と配布 | リポジトリを公開したまま、資格情報・到達手段・実データが公開される場所（追跡ファイル・CI のログ・成果物）に現れない |
| `N-10` 公開と配布 | ストアへ届くのは、オーナーが明示的に承認したものだけ |
| `N-11` 公開と配布 | CI に置く鍵は、漏れても失効・再発行で回復できるものに限る |

**N-01〜N-09 は各文書で既に決まっていたものを集めたもの**で、新しい決定ではない（N-09 の「CI のログ・成果物」だけは範囲を広げた）。**N-10・N-11 は ⑤ のリリース整備で実現する**（[要件バックログ](../案件/22_要件バックログ.md)。起こした経緯は[決定ログ](./log_11_要求定義書.md) 2026-10-02）。

## 7. スコープ外

やらないと決めたもの。将来の候補は「候補」と明記する。

| 項目 | 扱い | 理由 |
|---|---|---|
| リストの共有・同期・アカウント | 対象外 | 対象ユーザーを一人で買い物する人に絞った（§3）。サーバーが要り、C-3 と衝突する |
| バックエンド全般 | 対象外 | C-3。同上 |
| レシピ・献立からの品目生成 | 対象外 | 買い物リストの範囲を超える。C-4 |
| 価格・家計簿・支出管理 | 対象外 | 同上 |
| バーコード読み取り・商品データベース連携 | 対象外 | 品目は自分の言葉で登録すれば足りる。C-4 |
| 店舗の地図・位置情報連動 | 対象外 | 「行く場所が決まっている」は品目の行き先で表現できる。C-4 |
| 英語ほか多言語対応 | **候補** | 初回は日本語のみ（§3）。文言はリソース化しておき（N-07）、必要になれば足す |
| タブレット・デスクトップ・Web への最適化 | 対象外 | 店内で片手で使うスマートフォンが利用環境（§3） |
| 既存データの移行・インポート | 対象外 | 未リリースであり移行元がない |
| 検索の同義語辞書・サーバー側検索・検索語の統計 | 対象外 | 辞書の運用が C-4 に、サーバーが C-3 に見合わない（[検索体験検討](../検討/31_検索体験検討.md) §6） |

## 8. 収益モデル（仮説）

- **無料＋広告**を基本とし、**サブスクリプションでプレミアム解除**（広告非表示を含む）を提供する
- **初回リリースは課金構造なし**でよい。広告・課金はユーザーがついてから ⑤ で導入する（要求としては F-501・F-502）
- 未決事項（④ の MVP 実装後に詰める。[決定ログ](./log_11_要求定義書.md) 2026-08-31）:
  - プレミアムで解除する機能は何か。C-4 に照らして、基本ループを有料化しない
  - サーバーを持たないアプリで、サブスクリプションが**継続して提供する価値**は何か。説明できなければ買い切りへ切り替える
  - 広告の表示位置。店内で使う画面（カゴ・チェック）の邪魔をしない

## 9. プラットフォームと技術方針

- **Android と iOS** の両方に出す。実装は Kotlin Multiplatform＋Compose Multiplatform で共有する（③）
- スマートフォンのみ。最低 OS バージョンは Android が minSdk 31、iOS が 26（③ で決定）
- データは端末内の SQLite（Room）。C-3
- 技術選定は「学びたいこと」を理由に選んでよいが、C-5（両 OS で同じ体験）を損なう選択はしない
- **iOS の画面の外枠（ナビゲーションバー）はネイティブ（SwiftUI）で持ち、中身を Compose で描く**。OS が用意する見た目・操作の作法をそのまま受け取るため。C-5 は機能の対等性を求めるもので、この構成と矛盾しない。**タブバーは持たない**——④ で[画面定義書](./13_画面定義書.md) §1 がプール（01）を唯一の根に決めたため（[決定ログ](./log_11_要求定義書.md) 2026-09-07）

## 10. 名称

- 開発中の仮称は **Re-Buy**。パッケージ名・リポジトリ内の識別子はこれに合わせる
- ストアに出す正式名称は、マーケティング観点（検索・識別性・商標）を含めて ⑤ で決める。仮称をそのまま採用する場合もある
- 「くりかえし使える買い物リスト」はコンセプトを説明する言葉として、ストアのサブタイトル等で使う
