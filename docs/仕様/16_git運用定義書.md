## 1. git 運用ルール

### 1.1 リスク別ルーティング

変更の種類で入口を分ける。判断に迷ったらリスクの高い側（ブランチ＋PR）に倒す。

| 変更の種類 | 経路 |
|---|---|
| docs・軽微（typo・文言・挙動に触れない小修正）・ツール整備 | `main` 直コミット。push はオーナーの合図でまとめて行ってよい |
| コード・挙動の変更 | ブランチ → PR → CI 緑 → オーナー動作確認 → **合図で squash マージ** |

未リリースの間は push ＝ デプロイではない。ストア公開後（ロードマップ ⑤）にリリースブランチの扱いを本書へ足す。

### 1.2 ブランチ命名

- **`<id>-<slug>`**。すべて小文字、使える文字は `a-z 0-9 -` のみ。スラッシュは使わない
- `id` は台帳の ID をそのまま小文字にしたもの: `t-XX`（技術改善バックログ 23）、`f-XXX` / `n-XX`（要求。④ 以降）、`fb-XX`（ユーザーフィードバック 21。④ 以降）。ID の無い作業は先に台帳へ起票する
- **1 ブランチ＝1 PR。ブランチは使い回さない**。マージ時にリモートブランチは自動削除される（リポジトリ設定）。ローカルは squash のためマージ検出できないので、マージ済みを確認のうえ `git branch -D` で消す
- **ブランチは push 済みの main から切る**。squash は派生元からの全差分を 1 コミットに畳むので、未 push のコミットが main に残ったまま切るとその内容まで PR に取り込まれる。切る前に `git status -sb` で ahead が無いことを見る
- `dependabot/*` ブランチはこの命名の対象外

### 1.3 マージ規律

- **push・マージは常にオーナーの合図が前提**。自動マージ・ブランチ保護は設けない
- マージ方式は squash のみ（merge commit / rebase はリポジトリ設定で無効）
- CI（`docs`・`build`・`instrumented`）が緑でないものはマージしない

### 1.4 pre-commit フック

`.githooks/pre-commit` が `python3 scripts/check-ios-signing.py --staged` を回し、署名にまつわる設定が追跡ファイルに入ったコミットを止める。

- **clone したら 1 回だけ `git config core.hooksPath .githooks` を実行する。** `.git/hooks` は追跡できないので、この設定が無いとフックは**エラーも出さずに無効**になる（README のセットアップにも同じ手順がある）。設定漏れの保険として、`verifier` もコミット前に同じ検査を回す
- フックが見るのは **index**（作業ツリーではない）。手元で書き換わっただけの状態はコミットに入らないので、そこで止めても `--no-verify` を覚えるだけになる
- **CI の `docs` ジョブが同じ検査を作業ツリーに対して回す。** フックは `--no-verify`・設定漏れ・**cherry-pick / revert / rebase / merge**（`pre-commit` が走らない）ですり抜けるので、CI が最後の網
- ただし **CI は push 後にしか鳴らず、public リポジトリでは push した時点で公開済み**——予防できるのはフックだけで、CI は「気づける」だけ
- **残る穴**: (a) トピックブランチを push したが PR を開いていない間は鳴らない（CI は PR と main への push で走る。ブランチは push と同時に PR にする運用なので窓は短い）。(b) **CI が見るのはその時点のツリーだけ**なので、汚したコミットを後のコミットで直すと 1 度も検査されないまま履歴に残る（[T-57](../案件/23_技術改善バックログ.md#t-57)）
