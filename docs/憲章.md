## 1. 背景

世に多くある買い物リストアプリは、**品目を追加し、店でチェックし、削除する**という単発型が大半である。しかし日常の買い物——とくにスーパーや薬局——で買うものは、毎回ほとんど同じ品目である。単発型のリストでは、同じ品目を毎回入力し直すことになり、その手間がリストを使う気を削ぐ。

もう一つ、一人暮らしの社会人には、買い物を含む家事を後回しにしがちだという事情がある。「何を買うか」「どこへ行くか」を考えるところから始めると腰が重い。逆に、**やることも行く場所も決まっている**状態が先にできていれば、あとは出かけるだけになる。

本プロジェクトのオーナーは、この 2 つを自分の問題として持っており、既存のアプリではどちらも解決しなかった。2023 年に自分で作り始め、動機は 2026 年の時点でも変わっていない。

## 2. 目的

くりかえし買うものを一度登録すれば、以後は入力なしで買い物に出かけられるリストを手に入れる。それによって、買い物という家事の腰を軽くする。

### 2.1 成功基準

次の 2 つが両方満たされたとき、本プロジェクトは成功したと言う。

1. **オーナー自身が毎週の買い物で使い続けている**（他のメモ手段に戻らない）
2. **App Store と Google Play の両方で公開され、オーナー以外の人が使っている**

収益化は目標であり、グロースの活動はロードマップ ⑤ で行うが、**収益の有無は成功の必要条件にしない**。KMP と AI 主導開発の習得はプロジェクトの動機の一つだが、成果物ではなく副産物として扱う。

## 3. 対象ユーザーと利用シーン

- **対象ユーザー**: 自分の分の買い物を自分でする人。典型は一人暮らしの社会人。オーナー自身がその一人であり、最初のユーザーでもある
- **共有しない**: 家族やパートナーとリストを共有する世帯は対象にしない（§6）。リストは一人のものとして設計する
- **利用シーン**:
  - 平時: 切れそうなもの・欲しいものに気づいたとき、登録済みの品目をカゴへ入れる（数秒の操作）
  - 出発前: カゴの中身を見て「今日はこれを買いに行く」と決める
  - 店で: カゴの品目を見ながら棚を回り、取ったものにチェックを入れる
  - 会計後: 「買い物を終わる」でチェック済みの品目をプールに戻す。次回はまたカゴへ入れるだけ
- **利用環境**: スマートフォン（Android / iOS）。店内で片手で使う。通信がなくても動くこと
- **市場・言語**: 初回リリースは日本市場・日本語のみ。英語対応は将来の候補（§6）

## 4. コンセプト: くりかえし使える買い物リスト

品目を使い捨てにしない。品目は**プール**に常駐し、買い物のたびに**カゴ**を経由してプールへ戻る。

```
プール（登録済みの品目）──カゴへ入れる──▶ カゴ（今日買うもの）──店でチェック──▶ チェック済み
   ▲                                                                              │
   └───────────────────────── 「買い物を終わる」でプールへ戻る（最終購入日を記録）──┘
```

- 品目にはカテゴリを付けられ、プールはカテゴリで絞り込める（スーパー用・薬局用のように使う）
- 品目は最終購入日を持つ。「前に買ったのはいつか」がプールで分かる
- カゴに入っていない品目は削除されない。次に必要になったときにまたカゴへ入れる

この基本ループは実装済みである。ロードマップ ④ では、このループを崩さずに「腰を軽くする」方向へ体験を磨く。

## 5. 重視する価値

機能の要否や優先度で迷ったとき、次の順で判断する。番号は要求定義書からの参照用。

| ID | 価値 | 意味 |
|---|---|---|
| C-1 | **繰り返しの入力をゼロに近づける** | 一度登録した品目は二度と打たない。カゴへ入れる・チェックする・戻す、の操作だけで回る |
| C-2 | **腰を軽くする** | 起動から「買い物に行く」までが最短。「何を買うか」「どこへ行くか」を考えなくて済む状態を先に作る。この価値は C-1 の帰結ではなく、独立した目的として扱う |
| C-3 | **端末内で完結する** | アカウントなし、サーバーなし、オフラインで動く。データは端末の中にあり、外へ出ない |
| C-4 | **単純さ** | 機能を足すより、基本ループの速さと分かりやすさを守る。迷ったら足さない |
| C-5 | **両 OS で同じ体験** | Android と iOS で機能・操作感を揃える。片方だけの機能を作らない |

価値が衝突したら小さい番号を優先する。ただし C-3 は前提であり、C-1・C-2 のために C-3 を崩す（サーバーを持つ）ことはしない。

## 6. スコープ外

やらないと決めたもの。将来の候補は「候補」と明記する。

| 項目 | 扱い | 理由 |
|---|---|---|
| リストの共有・同期・アカウント | 対象外 | 対象ユーザーを一人で買い物する人に絞った（§3）。サーバーが要り、C-3 と衝突する |
| バックエンド全般 | 対象外 | C-3。同上 |
| レシピ・献立からの品目生成 | 対象外 | 買い物リストの範囲を超える。C-4 |
| 価格・家計簿・支出管理 | 対象外 | 同上 |
| バーコード読み取り・商品データベース連携 | 対象外 | 品目は自分の言葉で登録すれば足りる。C-4 |
| 店舗の地図・位置情報連動 | 対象外 | 「行く場所が決まっている」は品目のカテゴリで表現できる。C-4 |
| 英語ほか多言語対応 | **候補** | 初回は日本語のみ（§3）。文言はリソース化しておき、必要になれば足す |
| タブレット・デスクトップ・Web への最適化 | 対象外 | 店内で片手で使うスマートフォンが利用環境（§3） |
| 既存データの移行・インポート | 対象外 | 未リリースであり移行元がない |

## 7. 収益モデル（仮説）

- **無料＋広告**を基本とし、**サブスクリプションでプレミアム解除**（広告非表示を含む）を提供する
- **初回リリースは課金構造なし**でよい。広告・課金はユーザーがついてから ⑤ で導入する
- 未決事項（④ で詰める）:
  - プレミアムで解除する機能は何か。C-4 に照らして、基本ループを有料化しない
  - サーバーを持たないアプリで、サブスクリプションが**継続して提供する価値**は何か。説明できなければ買い切りへ切り替える
  - 広告の表示位置。店内で使う画面（カゴ・チェック）の邪魔をしない

## 8. プラットフォームと技術方針

- **Android と iOS** の両方に出す。実装は Kotlin Multiplatform＋Compose Multiplatform で共有する（ロードマップ ③）
- スマートフォンのみ。最低 OS バージョンは ③ で決める（現状 Android は minSdk 31）
- データは端末内の SQLite（Room）。C-3
- 技術選定は「学びたいこと」を理由に選んでよいが、C-5（両 OS で同じ体験）を損なう選択はしない

## 9. 名称

- 開発中の仮称は **Re-Buy**。パッケージ名・リポジトリ内の識別子はこれに合わせる
- ストアに出す正式名称は、マーケティング観点（検索・識別性・商標）を含めて ⑤ で決める。仮称をそのまま採用する場合もある
- 「くりかえし使える買い物リスト」はコンセプトを説明する言葉として、ストアのサブタイトル等で使う

## 10. 前提と制約

- 個人開発。趣味ペースで、日付ではなく順序で進める（ロードマップ §2）
- 開発は AI 主導（Claude Code）で行い、その体制はロードマップ ② で整える。仕様が正でコードは従う
- リポジトリは公開する予定。到達手段・資格情報・実データにつながる記述はコミットしない
