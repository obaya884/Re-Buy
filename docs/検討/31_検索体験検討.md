## 1. 動機

FB-10 で「打ち方の揺れ」を畳んだ（かなとカナ・全角と半角・英字の大小）。**漢字と読みの同一視は明示的に持ち越し**になっており、それ以外にも打ち手が残っている。ここは実装の待ち行列ではなく、**どれが要るかを決めるための材料置き場**。

## 2. 問題は 2 つに割れている

検索が「使いにくい」には別の症状が 2 つあり、効く手が違う。

| 症状 | 中身 | FB-10 との関係 |
|---|---|---|
| 再現率 | 打った語で当たらない。探しものがあるのに出てこない | **FB-10 が潰した層**。畳めば当たりは増える |
| 精度・順序 | 当たりすぎて目的の行が埋もれる。上から順に目で追うことになる | **FB-10 が悪化させた層**。畳んだぶん当たりが増えた |

**品目が増えるほど後者が効く。** プールは「くりかえし使える」置き場なので品目は減らずに積み上がり、当たりの件数は時間とともに増える一方になる。したがって次に効くのは「当てる」ではなく「上に出す」だと見ている。

## 3. 候補

| ID | 案 | 効く症状 | 効果 | コスト | 価値軸との関係 | 仕様判断 |
|---|---|---|---|---|---|---|
| A | 当たりを**入力で始まるもの優先**に並べる | 精度 | 中〜大 | 小。畳んだキーで前方一致を見る比較関数 1 つ | C-4 と衝突しない。増えるのは並びだけで操作は増えない | 要。05 は「登録順」と明記 |
| B | **空白・記号を畳む** | 再現率 | 中 | 極小。`SearchKey` に枝 1 つ | 誤爆がほぼ無く、今の畳み込みの自然な延長 | 小。13 §05 の畳む範囲に 1 項 |
| C | 05 の初期表示を**最近買ったもの**寄りに | どちらでもない | 中 | 小。`lastBoughtAt` は既にある | **C-2 に直接効く**。検索を打つ回数そのものが減る | 要。05 は「登録順」 |
| D | **0 件のときだけ緩める**「もしかして」 | 再現率 | 中 | 中 | **当たっているときの精度を下げない**のが要。緩めを常時かけない | 要。セクションが 1 つ増える |
| E | カテゴリ名・行き先名も検索対象に | 再現率 | 中 | 小〜中 | 「思い出す」に効く。「他の行き先から」との噛み合わせが要る | 要 |
| F | 品目に**別名**を持たせる | 再現率 | 大 | 大。列＋Migration＋06 の UI | C-1・C-4 と衝突。ただし任意なので基本ループは変わらない | 要 |

補足が要るものだけ書き下す。

### A 前方一致を優先する

畳んだキーで `startsWith` かどうかを見て、当たりを 2 群に分けるだけ。**群の中の並びは登録順を保つ**ので、「登録順」という既存の規則を捨てるのではなく 1 段だけ挟む形になる。13 §05 の「並びは登録順」を書き換える必要がある。

### D 0 件のときだけ緩める

長音の有無・小書き・促音の揺れ、編集距離 1 のあいまい一致は、**常時かけると誤爆が増えて A の効果を打ち消す**。「当たりが 0 件のときだけ」に閉じ込めれば、当たっている場面の精度は一切下がらない。セクション「もしかして」を 1 つ足す形になる。

### F 別名

品目に任意の別名を持たせ、ユーザーが「読み」でも「言い換え」でも足せるようにする。**G の代替になる**——機械の推測より確実で、両 OS で同じ結果になり、辞書も要らない。基本ループ（登録して、カゴへ入れて、チェックする）には触らないので C-1 は保てる。代償は 06 の UI が 1 段増えること。

## 4. G（漢字と読み）が重い理由

読みを機械で取る道は、**両 OS で同じ結果にならない。**

- iOS には日本語のトークナイザから読みを引く手がある
- Android に同等のものが無い。ICU の `Han-Latin` は日本語の読みではなくピンインを返す
- 揃えるには辞書を積むことになり、数 MB がアプリサイズに乗る

これは **C-5（両 OS で同じ体験）のために C-4（単純さ）を払う**構図で、FB-10 でプラットフォームの正規化 API を避けたのと同じ理由が、より大きな規模で当てはまる（[log_13](../仕様/log_13_画面定義書.md) 2026-09-06）。

**したがって順序は F が先。** F を入れて空振りが止まるなら G は要らない。F でも止まらないと分かってから初めて、辞書のコストを検討する意味が出る。

**上の 3 点は当たり直していない見立て**なので、G に着手するなら最初に裏取りする。

## 5. 勧める順

**B → A → C** をひと組。ここまでは仕様判断が軽く、コストが小さく、C-4 に触らない。**D・E・F は使ってみてから。**

## 6. 却下・スコープ外に落とすもの

| 案 | 扱い | 理由 |
|---|---|---|
| ローマ字入力での一致（`miruku` で当たる） | 見送り | 表だけで書けて辞書も要らず両 OS で同じになるが、日本語 IME を使う限り効く場面が無い。効果が小さい |
| 同義語辞書の内蔵 | 対象外 | 辞書のサイズと更新の負担が C-4 に見合わない。F がユーザーの手で同じことを解く |
| サーバー側の検索・辞書 API | 対象外 | C-3（端末内で完結）。[要求定義書](../仕様/11_要求定義書.md) §7 の既存の判断がそのまま当たる |
| 検索語の統計を端末内に貯めて自動改善 | 見送り | 一人用のアプリで統計が貯まるほどの母数が無い。オーナーの FB のほうが速くて正確 |

## 7. 次に測ること

**どれが要るかは品目数と実際の空振りに依り、今は憶測でしかない。** C-4 は「迷ったら足さない」なので、憶測で足さずに次を集める。

- **空振りした語**——「◯◯で打ったら△△が出なかった」を [FB 台帳](../案件/21_FB台帳.md)へそのまま書き留める
- **埋もれた場面**——当たりすぎて上から目で追うことになった場面
- **そのときの品目数**——A・C が要るかは件数に強く依る

数件たまった時点で、上の表のどれが要るかが決まる。**空振りが漢字と読みに集中するなら F、当たりの多さに集中するなら A**、という読み方をする。
