# 決定ログ — 機能・UX 見直し検討

[本文](./33_機能UX見直し検討.md)の判断の経緯を日付順で積む。

## 2026-08-31 ④ 着手ブレスト（オーナーとの対話で確定）

- **買い物を「モード」にした理由**: 出発前の「買い物リスト」タブと買い物タブの情報がほぼ重複しているというオーナーの実感。平時の確認（開始シート）と店内のチェック（モード画面）に役割を分けることで重複を解消する
- **カテゴリと行き先を分けた理由**: 憲章の「カテゴリ＝行く場所」はオーナーの実態（カテゴリ＝食料品・生活用品のような区別）とずれていた。「どこへ行くか考えなくて済む」（C-2）を支える仕組みが別途必要で、行き先を独立概念として起こした。品目 1 つにつき行き先 0..1 のみ許すのは多対多の重さ（C-4）を避けるため
- **行き先の必須化は否決**: 追加の軽さ（名前だけで確定）と衝突する／初回起動に壁ができる／「その他」という店名で行き先なしが名前を変えて復活するだけ／削除時の付け替え UI が重くなる、の 4 点
- **「どこでも買えるもの」への意味反転**: 行き先なし専用のモードを持つ代わりに、行き先なしの品目をすべてのモードに出す（オーナー発案）。「未整理」ではなく「どこでも買える」という正当な意味を与え、常に付き纏うことが行き先を整理する動機にもなる。これによりモードの一覧が純粋に DB から導出でき、画面セッション状態が不要になった
- **行タップ＝カゴ出し入れ／長押し＝編集**: 当初は行タップ＝編集だったが、最頻操作（出し入れ）との競合と誤操作ストレスをオーナーが懸念。誤操作コストの非対称（トグルは押し直せば戻る、編集シートの誤表示は毎回ストレス）に合わせて逆転させ、「長押し＝編集シート」をアプリ全体の共通作法に広げた（カテゴリ・行き先管理の鉛筆アイコンも廃止）
- **足すシートを検索型にした理由**: 検索範囲を絞ると「範囲外に同名品がある → 見つからない → 登録しようとして重複エラー」の行き止まりができる。全品目を検索対象にし、追加済みは「追加済み」表示、他の行き先は別枠表示で解決した
- **他の行き先のヒットは「思い出しの追加」**: 当初案は「モード中に足した品目はそのモードに出す」（画面セッション保持）だったが、オーナーの想定は「その行き先のカゴに入るだけ」。こちらの方が単純で、プロセス死で表示が消える既知問題も消滅する。画面に変化が見えない点はスナックバーの通知で補う
- **登録ボタンを固定文言にした理由**: 品目名を埋め込むと長い名前でフォントサイズの動的調整が要る（オーナー指摘）。名前は直上の入力欄に見えているため「この名前で登録する」で足りる。キーボード確定で登録しないのは、日本語 IME の変換確定と紛れるため（登録の操作権をユーザーのタップに置く）
- **足すシートの自動クローズ**: 店内の追加は 1 件ずつが最頻なので最小手数（開く → タップ）に倒す。登録シートの「続けて登録」と逆の判断だが、自宅でまとめて登録する場面と店内の割り込み操作で場面が違う
- **語彙の統一**: 「品目を追加」が「新規作成」と「買うものに入れる」の両方を意味していた衝突を「登録／追加」の書き分けで解消（オーナー指摘）。「品目」は堅い語感のため UI には出さず、動詞・実名・「もの」で語る（「未追加のものから選ぶ」「行き先を選ぶと、買い物が始まります」）
- **品目の並び順を登録順にした理由**: 五十音順は SQLite の日本語照合が当てにならず、手動並び替えは品目数の多い一覧では重い。不満が出たら FB で拾う
- **開始シートのプレビューを先頭 2 件固定にした理由**: 全件連結の 1 行切り詰めでも長い（オーナー指摘）。全体量は件数が伝えるので「など」も付けない
- **行き先チップの 🏬**: システムが表示時に前置する（ベクタアイコン案はオーナーが絵文字を選択）。ユーザーの絵文字入力は禁止しないが、システムは名前に何も足さない
- **テーマ選択を MVP に含め既定を藍にした**: 配色 3 案（若葉・藍・柿）をモックで比較してオーナーが決定
- **収益の未決事項は MVP 実装後へ**: 使えるプロダクトになる前に有料化の線引きをするのは早すぎる（憲章 §7・§11 を更新）
- **モックの位置づけ**: ブレスト中に作った 10 画面の HTML モックを guide_33 として取り込み、画面定義書（13）を書くまでの見た目・挙動の正とする
