# ロードマップ 決定ログ

- [ロードマップ](./24_ロードマップ.md) の「なぜそうしたか」を日付順に積む。本文は現在の計画だけを持つ

| 日付 | 決定 | 理由 |
|---|---|---|
| 2026-08-29 | 憲章を先頭に置く | 「iOS が要るか」「バックエンドが要るか」「何を収益化するか」がすべて憲章で決まり、KMP の構造にも影響するため |
| 2026-08-29 | KMP を機能見直しより前に置く | KMP を学ぶこと自体が目的の一つであり、コードが約 45 ファイルの今が移植コスト最小。④ の新機能は最初から KMP 側に書けばよい |
| 2026-08-29 | ③ を「挙動を変えない移植」に限定する | 移植と機能追加を混ぜると、壊れたときにどちらが原因か切り分けられないため |
| 2026-08-29 | Android MVP を先に作って使い込んでから KMP、という順は採らない | プロダクトとしては王道だが、学習を先延ばしにする理由が無いため |
| 2026-08-29 | hitosuji の仕組みは段階的に採用する | hitosuji は実運用中の web アプリの前提で組まれており、未リリースの Android アプリに丸ごと入れても回らない。FB 台帳は実利用が始まってから、監視項目はリリース後 |
| 2026-08-31 | ③ は段 4 を残して中断し、④ へ進む | 段 3 で iOS シミュレータに全画面が出て、CI も 4 ジョブになった。残る段 4（外枠を SwiftUI へ）は **利用者から見た価値を生まない**——iOS を配るのは ⑤ なので、外枠がネイティブかどうかは誰にも届かない。対して ④ は「オーナーが自分で使い始める」で終わる。加えて ④ で画面構成が変われば外枠は作り直しになる。ロードマップの「各サブプロジェクトが単独で価値を残す」原則にも反しない——段 3 は既に価値を残している。**ただし ④ の前に iOS の網（T-42）を入れる**。詳細と iOS 案件の順序は log_23 |
