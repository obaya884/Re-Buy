## 1. 何をするか

iOS の外枠（ナビゲーションバー）を SwiftUI に載せ替え、Compose の中身がその下を流れるようにする。**Android の挙動と見え方は変えない。**

## 2. 採る形（案 C）

**SwiftUI は `NavigationStack` を 1 段だけ置き、ツールバーを持つ。画面の切り替えは今までどおり Compose の `NavDisplay` が行う。**

比べた 3 案と、採らなかった理由。

| 案 | 中身 | 採否 |
|---|---|---|
| A | SwiftUI が `NavigationStack` の path を持つ | **採らない。** Navigation 3 を iOS で捨てることになり、`NavigationState` が苦労して守っているプロセス復元を作り直す。**`iosTest` の遷移の網（10 ファイルのうち画面をまたぐ検証）が消える** |
| B | Kotlin が持ち、SwiftUI がミラーする | **採らない。** UIKit に push を描かせるには結局画面ごとに VC を割ることになり、実装量は最大で得られるものは A と同じ |
| C | SwiftUI は 1 段。ツールバーだけ持つ | **採る。** Liquid Glass は付く。Nav3・`Navigator`・`NavigatorTest` と `iosTest` 10 ファイルが温存できる。**後から A へ移れる**（バーの橋は A でも要る資産） |

**案 C で付かないもの**を先に書く。

- **ネイティブの端スワイプ戻り**——`NavigationStack` が 1 段なので pop 先が無い。ただし**いま iOS で端スワイプが戻りになるかは OS の版で変わる**（[T-62](./23_技術改善バックログ.md#t-62)）ので、確実な戻り道はもともとバーの ← だけ
- **遷移中にバーが中身と一緒に動くこと**——中身は Compose がスライドさせ、バーは別に切り替わる
- **スクロール端の効果**（iOS 26 でバーの縁がスクロールに応じて変わるもの）——`UIScrollView` と連動する仕掛けなので、中身が Compose である限りどの案でも付かない

## 3. スパイクで測ったこと（2026-09-07）

コミットしない検証で、設計の前提を 5 つ確かめた。

| # | 見たこと | 結果 |
|---|---|---|
| a | 端スワイプで戻れるか | **iOS 26.5 では効かない**（測ったのはこの版。その後 18.2 と 26.0 では効くと分かった）。[T-62](./23_技術改善バックログ.md#t-62) と [FB-18](./21_FB台帳.md#fb-18) へ |
| b | バーの背後をコンテンツが通るか | **通らない。** c の裏返しで、**top inset を意図的に消費しない作業が要る**（Step 5） |
| c | `WindowInsets.safeDrawing.top` にバー高が入るか | **入る。** Compose のアプリバーがきっちり押し下げられた。**Swift から高さを渡す橋は要らない** |
| d | Compose のシートがバーを覆うか | **覆う。** スクリムがガラスのカプセルまで暗くする。Swift 側でスクリムを重ねる対処は不要 |
| e | 下部 CTA がホームインジケータを避けているか | **すでに避けている。** CTA は `Scaffold` の `content` の中にあり `contentWindowInsets` が bottom を渡している |

**見出しの二重化も実物で出た**——SwiftUI の見出しと Compose のアプリバーが縦に 2 つ並ぶ。Step 1〜3 はこれを解く作業。

## 4. 段取り

**ビルドを緑に保ったまま進む。** Step 4 まで見た目は変わらない。

| Step | 内容 | 触る場所 | 見た目 |
|---|---|---|---|
| 1 | `ReBuyAppScaffold` のバーを**スロットからデータへ**（`title` / `accessory` / `back` / `actions` / accent）。既定のレンダラは今の `TopAppBar`。**使われていない `bottomBar` と FAB 2 引数を落とす** | `:shared:ui` | 不変 |
| 2 | バーの描き手を差し替えられるようにし、**画面ごとの bar state を commonTest で見る** | `:shared:ui` | 不変 |
| 3 | iOS の入口に「バーを描かない版」と、bar state の購読口を足す | `iosMain` | 不変 |
| 4 | `ContentView` を `NavigationStack` ＋ `.toolbar` にして繋ぐ。あわせて `Config.xcconfig` の `IPHONEOS_DEPLOYMENT_TARGET` を **17.0 から 26.0 へ**（[11](../仕様/11_要求定義書.md) §9 が「最低 iOS 26」と定めているのに実装が追随していなかった。Liquid Glass も 26 前提） | `iosApp` | **変わる** |
| 5 | 中身をバーの下へ流す。**Android では足す値が 0 になる形にする** | `:shared:ui` | iOS だけ変わる |
| 6 | `iosTest` 10 ファイルを橋の向こう側へ向ける（タグは据え置き） | `iosTest` | — |
| 7 | Release framework を足し、[17](../仕様/17_テスト戦略定義書.md) §5 の実機ステップを Release へ伸ばす。§6 の該当行を書き換える | `:shared:ui` ／ CI ／ docs | — |

### 各 Step の勘所

- **Step 1 の「データへ」**: アイコンの渡し方と色の渡し方は [13](../仕様/13_画面定義書.md) §6 に条項がある。**既定のレンダラを今の `TopAppBar` にする**のが Android を変えない仕掛けで、ここを外すと 6 画面と instrumented がまとめて動く
- **Step 2 で網が 1 段降りる**: いま `TOP_APP_BAR_TITLE` を引いて見ている「画面の同定」が、**UI 段からロジック段（bar state）へ**降りる。Step 6 の書き換えに強くなる
- **Step 4 で 04 の戻るを繋ぐ**: バーの ← は「1 つ戻る」ではなく**画面が決めた動作**を呼ぶ。04 はそこに離脱確認を繋ぐ（[13](../仕様/13_画面定義書.md) §6）。**素通りさせるとチェックした内容が確認なしで失われる**
- **Step 5 が「Android を変えない」の勘所**: `innerPadding` をそのまま解釈だけ変えて使うと、**Android でも行がバーの下へ潜り込む**。足す値が Android で 0 になる形にする
- **Step 6 は変異で確かめる**（[17](../仕様/17_テスト戦略定義書.md) §2.2）: publish 側の title を壊して、狙ったファイルだけが落ちるか

## 5. 網について

- **Android のテストが 1 件も網にならない**（iOS だけを触るため）
- **`iosTest` 16 ファイル中 10 ファイルが外枠のタグに依存している**。案 C ならタグ据え置きで済むが、**検証対象は bar state へ移る**
- **薄くなるのは「Swift がその state を実際にバーへ描いているか」の 1 点**だけ。これは [T-46](./23_技術改善バックログ.md#t-46) の守備範囲そのもの
