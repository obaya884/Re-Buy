# 技術改善バックログ

- 作成日: 2026-08-29
- 目的: 技術負債の返済・リファクタリング・開発ツール整備など、**プロダクト挙動を変えない技術活動**を、要求（F-XXX / N-XX）とは別軸で管理・計画する
- 関連文書: [要件バックログ](./22_要件バックログ.md)（プロダクト軸の台帳）

## この文書の守備範囲

プロダクトの**挙動**に関わる変更は扱わない。ここに書くのは、ユーザーから見た挙動を変えずに**開発の健全性を上げる活動**——依存追随・CI/ツール整備・内部設計の改善・テスト補強・調査など。

- 採番は **T-XX**。1 系列で通し、種別で区別する
- 種別: **何に触るか＝着手時に何が網になるか**で分ける（下表）
- 優先度: `高` / `中` / `低` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`
- **1 エントリ＝[一覧](#一覧)の 1 行＋[詳細](#詳細)の 1 節**。一覧は索引に徹し `ID / タイトル / 種別 / 優先度 / 状態 / 詳細` の 6 列を持つ
  - **見出しは `### T-XX` の ID のみ**
  - **セル内に `|` を書かない**
  - **種別・優先度・状態を詳細節に書かない**。一覧が正
  - 詳細節の項目は `背景`（必須）に続けて `対応方針` / `着手条件` / `優先度の根拠` / `関連` を必要なだけ
  - 詳細節の並び順は一覧と同じにする
- **完了になったエントリは、状態更新と同じコミットで[closed_23_技術改善バックログ.md](./closed_23_技術改善バックログ.md)へ移す**（本書には未着手・進行中・保留だけを残す）。**一覧の行と詳細節はセットで移す**——`sh scripts/ledger-move.sh T-XX` が両方を移す
- 判断の経緯は本文に書かず、`log_23_技術改善バックログ.md` へ日付順に積む（最初のエントリが出た時点で作る）

### 種別

| 種別 | 何に触るか | 着手時に何が網になるか |
|---|---|---|
| 内部設計 | 本番コード（`androidApp/src/main`・`shared/*/src/{commonMain,androidMain,iosMain}`）の構造（挙動不変） | 既存テスト。**変異させて振る舞い保存を確かめる** |
| テスト | テストコードのみ（本番コード不変） | 本番コードに触れないので回帰の心配がない |
| ツール整備 | `scripts` / CI / `.claude` / 開発環境 | **自動テストの網が無い**。実行して確かめる |
| 依存追随 | 依存ライブラリ・Gradle・AGP の更新 | 上流待ちが多く自分では動かせない。**再確認の契機を必ず書く** |
| 調査 | 何も変えない。判断を記録する | 成果物は決定そのもの |

## 詳細

### T-11

- 背景: `instrumented` ジョブは毎回 Android Emulator（約 300MB）と aosp-atd のシステムイメージ（約 500MB）をダウンロードしている。`actions/cache` でイメージのディレクトリだけを復元すると、GMD が emulator の導入をスキップして `pixel6Api35Setup` が失敗した（main の run 33232649012）
- 対応方針: キャッシュするなら `$ANDROID_HOME/emulator` と `system-images/android-35/aosp_atd/x86_64` の両方を、emulator のバージョンをキーに含めて復元する。効果（短縮時間）を計測してから採否を決める
- 着手条件: instrumented ジョブの所要時間が気になり始めたら。public 化後は実行時間が無制限なので急がない

### T-12

- 背景: `ci.yml` の Action は major タグ固定（`@v7` 等）。現状はトークンが `contents: read` でシークレット参照も無く、Dependabot が追随するので妥当な水準
- 対応方針: ⑤ で署名鍵を CI に持ち込む段階で、各 Action をコミット SHA に固定する（Dependabot はコメントのバージョン表記を頼りに SHA も更新できる）
- 着手条件: CI にシークレットを入れるとき

### T-17

- 背景: `RoomMigrationTest` は assert が 0 件・`ALL_MIGRATIONS` が空・`runMigrationsAndValidate` 未使用で、実質「現行バージョンの DB が開ける」ことだけを見る煙テスト。T-24 で `version = 2` に上げたが Migration を書かなかったため、検証対象の遷移がまだ 1 本も無い
- 対応方針: `runMigrationsAndValidate` へ切り替え、`ALL_MIGRATIONS` に追加した `Migration` を登録する
- 着手条件: 最初の `Migration` を書くとき（＝公開後にスキーマを変えるとき。CLAUDE.md「スキーマ変更時の手順」と同時に行う）
- 関連: T-13 のレビューで test-reviewer が指摘

### T-21

- 背景: instrumented テストは本物の `ReBuyApplication`（Koin を起動する）の上で走り、DB を差し替えていないため、端末の本番 DB を読み書きする。使い捨てのエミュレータ（GMD）では実害が薄いが、実機で `connectedAndroidTest` を回すとオーナーの実データに依存し、要求定義書 §11 の姿勢とも噛み合わない。DB を用意できないことが理由で「買い物を終わるとホームへ戻る」「空状態のボタンからアイテム一覧へ遷移する」の 2 経路が自動化できず手動確認に残っている
- 対応方針: `loadKoinModules` で `AppDatabase` の定義を in-memory のものに差し替え、DAO へ直接シードしてから画面を操作する形にする。テスト側で `startKoin` を呼ぶと本物の `Application` と衝突するので、差し替えは `loadKoinModules` / `unloadKoinModules` で行う。そのうえで上記 2 経路を自動化する。あわせて `ViewModelScopeTest` の逆向き（entry が backstack に残っている間は ViewModel が保持されること）も書く——買い物画面の終了確認ダイアログを開くのにチェック済みの品目が要るため、シードできるようになって初めて書ける
- **追記（2026-08-31、T-48 の実測から）: 差し替えの機構は確かめたが、Android では順序が問題になる。**
  - **機構は使える。** `startKoin { allowOverride(false) }` は**起動時の `modules()` にしか効かず**、起動後の `loadModules` は既定で `allowOverride = true`（Koin 4.1.0 のソースで確認）。本番の方針を緩めずに差し替えられる
  - **ただし上書きは「これから作るもの」にしか効かない。** `AppDatabase` → DAO → Repository はすべて `single` なので、1 度でも解決された後に差し替えても Repository は古い DAO を掴んだままになる（iOS で実測）
  - **Android は iOS より条件が厳しい。** iOS はテスト自身が Koin を起動するので解決前に差し込めたが、Android は本番の `ReBuyApplication` が**プロセス起動時**に Koin を立て、`createAndroidComposeRule<MainActivity>()` が `ActivityScenarioRule` で **Activity を起動してから**テスト本体へ入る。**テスト本体で `loadKoinModules` を呼ぶ頃には鎖が実体化している可能性が高い**
  - **ここは未実測。** ルールが `ActivityScenarioRule` を使うことはソースで確認したが、composition がどこまで進むかは測っていない。**着手時に最初にこれを測る**
  - 回避策の候補は 2 つで、どちらも代償がある。(a) `createComposeRule()` にして自分で `setContent { ReBuyApp() }` する——差し替えは効くが「**実物の `MainActivity` を起動している**」という価値が消える（[T-47](#t-47) が「移さない理由」に挙げたのと同じもの）。(b) テスト用の `Application` を用意する——起動前に差し込めるが `testInstrumentationRunner` まわりの仕掛けが増える
- 優先度の根拠: 実機でテストを回した瞬間に実データを触る。手動確認に残っている経路も減らせる
- 補足: `RoomMigrationTest` と `KoinGraphTest` は検証対象が `:shared:data` なのに `:androidApp` の androidTest にある（GMD を 1 本に保つための判断。段 2 の計画を参照）。そのため schemas の assets 指定がモジュール境界をまたぐ。**置き場所を動かすかは [T-47](#t-47) が持つ**——この案件と同時に決める
- 関連: T-18 のレビューで test-reviewer が指摘

### T-25

- 背景: T-24 の日時テストはコンバータ単体（純粋関数）で止まっており、DB を越える経路が未検証。押さえられていないのは 3 点。(a) 列の affinity が `INTEGER` であること——`2.json` はビルドのたびに生成し直されるので退行検知にならない、(b) `lastBoughtAt = null` の往復——Room が生成する null 分岐はコンバータの非 null シグネチャでは表現できず、`getString` → `getLong` へ経路が変わった箇所、(c) 旧 v1 の DB を持つ端末が起動時に落ちること——T-24 でオーナーが決めた挙動なのに、誰かが `fallbackToDestructiveMigration()` を足しても全件緑のまま通る
- 対応方針: (a)(b) は in-memory DB で DAO の往復を見る。(c) は `AppDatabase.getDatabase` が DB 名を固定して `INSTANCE` をキャッシュしているため、実データを触らずに production のビルダー設定を通せる形（テスト用に DB 名を差せる口）が要る
- **追加（2026-08-30、T-31 ステップ 8）**: (d) **旧経路で作った DB を新経路で開けること**。本番の DB オープンは「framework SQLite ＋ 相対名」から「`BundledSQLiteDriver` ＋ 絶対パス」へ変わったが、これを通るテストが 1 本も無い。手動のアップグレードインストールでしか確かめていない。データ消失という最悪の失敗モードに対して網が無い
- 着手条件: T-21 で in-memory DB への差し替えを入れるとき。同じ足場を使う
- 優先度の根拠: (c) はデータが黙って消える方向への退行を素通しする。ただし ⑤ までは守るべき実データが無いので急がない
- 関連: T-24 のレビューで test-reviewer が指摘

### T-30

- 背景: `main` にブランチ保護が無く、必須チェックも設定していない。そのため CI が pending のままでもマージできる。実際に T-29 で `gh pr merge --auto` を使ったところ、必須チェックが未設定のリポジトリでは auto-merge が成立せず即マージにフォールバックし、`build` と `instrumented` が走り切る前にマージされた（結果は緑だったが、それは結果論）。いまは「オーナーの合図」と「AI が CI を見る」という運用だけが守っている
- 対応方針: `main` にブランチ保護を設定し、`docs` / `build` / `instrumented` / `ios` を必須チェックにする。これで `gh pr merge --auto` が意図どおり働き、pending のままマージすることが構造的にできなくなる。**直コミットを塞ぐかは別問題**——[git 運用定義書](../仕様/16_git運用定義書.md) は docs と軽微な変更の `main` 直コミットを認めているので、その運用を壊さない設定にする（`Require a pull request before merging` は入れない、または管理者を除外する）
- 優先度の根拠: 機械で守れることを運用で守っている。一人開発なので事故の頻度は低いが、`--auto` の挙動のように「守っているつもり」になる形が最も危ない
- 関連: T-29 のマージで実際に踏んだ。[git 運用定義書](../仕様/16_git運用定義書.md) §1.1 のリスク別ルーティング

### T-33

- 背景: convention plugin が `rebuy.android.base`（application / library / KMP の 3 系統を `withId` で振り分ける）と `rebuy.kmp.ios`（iOS ターゲット）の 2 つに分かれている。前者は自分のファイル冒頭で「各モジュールの **Android** の土台」と宣言しているのに `:shared:*` の KMP 設定も抱えており、名前と役割がずれている。モジュール側は 2 つの id を書く必要があり、書き忘れの余地も残る
- 対応方針: 分ける軸を「プラットフォーム」から「**モジュールの原型**」に変える。`rebuy.kmp.library`（KMP の android ターゲット設定 ＋ iOS ターゲット）と `rebuy.android.app` の 2 つにすると、モジュール側の id が 1 つになり、名前と役割も一致する
- 着手条件: 段 3 が終わって `:shared:*` の形が固まってから。段 3 の途中は source set の付け外しが続くので、土台を動かすと切り分けが難しくなる
- 優先度の根拠: いまの形でも動く。読みやすさと書き忘れの余地の話なので急がない
- 関連: T-31 のステップ 6 のレビューで code-quality-reviewer が提案

### T-34

- 背景: 本番の DB オープンは T-31 ステップ 8 で `BundledSQLiteDriver` ＋ 絶対パスになったが、`RoomMigrationTest` は旧オーバーロード `Room.databaseBuilder(context, klass, name)` ＋ `openHelper` のままで、**framework SQLite の経路を開いている**。緑なのは「壊れなかった」からではなく「本番と違うものを見ている」から。⑤ で `Migration` を書き始めたとき、本番と違う経路で検証したことになる
- 対応方針: `MigrationTestHelper` の driver ベースのコンストラクタへ寄せ、`openHelper.writableDatabase.close()` を `db.close()` にする
- 着手条件: 最初の `Migration` を書くとき（T-17 と同時）。それまでは検証対象の遷移が 1 本も無い
- 優先度の根拠: いま緑なので急がないが、緑の意味が本来と違う
- 関連: T-31 のステップ 8 のレビューで test-reviewer と code-quality-reviewer が指摘

### T-36

- 背景: `shared/ui/src/commonMain/composeResources/values/strings.xml` の 49 件のうち 12 件がどこからも参照されていない。買い物の中断確認 4 件・ホームのボトムシート 4 件・設定の行 2 件・空状態の副文 2 件で、いずれも作られなかった画面の名残。**T-31 のステップ 11 で Compose Resources へ移したことで、Android lint の `UnusedResources` の視界からも外れた**——生成される `allStringResources` が全件を参照するので、今後増えても機械では気づけない
- 対応方針: ④ の機能見直しで「その画面を作るのか」を決め、作らないものは消す。あわせて未使用を機械で見つける手立てを置くかを決める
- 着手条件: ④ の要件定義のとき。消す・残すは要求の判断なので、それより前には決められない

### T-37

### T-56

- 背景: pre-commit フックは `git config core.hooksPath .githooks` を打った人にしか回らず、**打ち忘れは予防の網ごと黙って消える**（詳細は [git 運用定義書](../仕様/16_git運用定義書.md) §1.4）。この検査で予防できるのはフックだけなので、消えると残るのは push 後の検知だけになる
- 対応方針: README のセットアップ節（T-55 で追加済み）は人の注意力頼み。自動で気づける唯一の現実的な手は Gradle の設定フェーズで警告すること（`providers.exec` で引き、CI では黙る）。**判定は `.githooks` との等値比較にしない**——絶対パスでも他のフックフレームワークでも正当なので、`<hooksPath>/pre-commit` が実在して実行可能かで見る。等値で書くと正当な構成を誤検知し、警告を無視する習慣を作る。**`git rev-parse --git-path hooks` が未設定時の既定 `.git/hooks` まで解決してくれる**ので、`core.hooksPath` を自分で読んで分岐する必要は無い。ただし返る値は **cwd 相対**なので、実行するディレクトリをリポジトリルートに固定する。また「実在して実行可能」だけでは、**この検査を呼ばない pre-commit** でも緑になる（他のフックフレームワークを許す方針の裏返し）
- 着手条件: いつでも。ただし**限界を承知して入れる**——main 直コミットのルート（docs・軽微・ツール整備）は Gradle を通らないので、この経路では警告が出ない。警告は無視もできる。一方で**この網が守りたい iOS の作業は必ず Gradle を通る**ので、カバー範囲と危険の所在は一致している
- 優先度の根拠: 守っているものが「秘密の公開」なので、[T-57](#t-57) より重い。一方で一人開発かつセットアップは 1 回きり
- 関連: [git 運用定義書](../仕様/16_git運用定義書.md) §1.4

### T-57

- 背景: `check-ios-signing.py` が見るのは作業ツリーと index だけなので、**汚す commit → 消す commit を積む**と、ツリーは綺麗になり CI も pre-commit も緑のまま値が履歴に残る。コード変更は squash マージなので main の履歴には入らないが、**public リポジトリでは `refs/pull/N/head` が永久に残り、ブランチを消しても squash しても消えない**。main 直コミットのルートは squash を通らないので main の履歴に直接残る
- 対応方針: **差分ではなく全履歴を毎回舐める**。`push` イベントの `github.event.before` は新規ブランチと force push で `0000…` になり、その分岐を書き損ねると「異常時に素通り」——今回わざわざ塞いだ失敗方向とちょうど逆になる。全履歴なら分岐が要らない。`actions/checkout` の `fetch-depth: 0` が要る（実測 11.6 MiB / 281 commit、`git rev-list --objects --all` は 0.1 秒未満）。**パスを列挙する形で舐める**——`git log --all -- <paths>` のようにパスを定数で渡す形は、[T-55](./closed_23_技術改善バックログ.md#t-55) でわざわざ捨てた「置き場所を定数で持つ」設計への逆戻りになる。スクリプト側は「任意の rev」を読む第 3 の経路が要り、そこでは「必須 2 本が無ければ落とす」条項が iOS 導入前のコミットで全部落ちるので例外が要る——**その例外が新しい穴になりうる**
  - 着手時に踏まえる事実（実測）:
    - **`refs/pull/N/head` には `--all` では届かない**——`actions/checkout` は `fetch-depth: 0` でも `refs/pull/*` を取らないので、push 実行では走査対象外。届くのは `pull_request` 実行のほう。**この手で塞げるのは main とタグまで**——`pull_request` 実行で届くのもその PR の ref だけで、過去の PR の head には届かない
    - `ci.yml` の `cancel-in-progress` があるため、**「汚す push → すぐ消す push」は悪意も 2 回の緑も要らない**——前者の tree が 1 度も検査されないまま成立する。**`pull_request` 実行も見るのはマージ後の tree だけ**なので、1 つの PR の中で汚して直すと同じく 1 度も検査されない。
    - **tag と stash は誰も見ていない**。破棄したはずの中間コミットが `refs/tags/*` に残り、`git push --tags` / `--follow-tags` で公開されうる。`refs/original/*`（履歴書き換えのバックアップ）も同じ
- 着手条件: 未定。⑤ の公開前に判断する
- 優先度の根拠: いま露出しうるのは Team ID と組織名で、前者は Apple が配布物に載せる準公開の識別子、後者は commit の author 名として既に公開を受け入れている（[要求定義書](../仕様/11_要求定義書.md) §11）。回復不能な損害は小さく、衛生寄り。**ただし ⑤ で配布を自動化すると、網のスコープはプロファイル名・証明書・鍵まで広がる**ので、そこで見直す（あわせて fastlane の設定と `.github/workflows/*.yml` も走査対象に入れる。どちらも実値が入りやすい）。**plist / entitlements はここに含めない**——capability を足したときや archive したときの産物で、「Xcode が開いた拍子」には書かれないため恒久的に対象外。**入れても CI は push 後の検知にしかならず、予防にはならない**ことも承知しておく
- 関連: [git 運用定義書](../仕様/16_git運用定義書.md) §1.4

### T-58
