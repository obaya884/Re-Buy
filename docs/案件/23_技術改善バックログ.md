# 技術改善バックログ

- 作成日: 2026-08-29
- 目的: 技術負債の返済・リファクタリング・開発ツール整備など、**プロダクト挙動を変えない技術活動**を、要求（F-XXX / N-XX）とは別軸で管理・計画する
- 関連文書: [開発基盤検討](../検討/31_開発基盤検討.md) ／ [要件バックログ](./22_要件バックログ.md)（プロダクト軸の台帳）

## この文書の守備範囲

プロダクトの**挙動**に関わる変更は扱わない。ここに書くのは、ユーザーから見た挙動を変えずに**開発の健全性を上げる活動**——依存追随・CI/ツール整備・内部設計の改善・テスト補強・調査など。

- 採番は **T-XX**。1 系列で通し、種別で区別する
- 種別: **何に触るか＝着手時に何が網になるか**で分ける（下表）
- 優先度: `高` / `中` / `低` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`
- **1 エントリ＝[一覧](#一覧)の 1 行＋[詳細](#詳細)の 1 節**。一覧は索引に徹し `ID / タイトル / 種別 / 優先度 / 状態 / 詳細` の 6 列を持つ
  - **見出しは `### T-XX` の ID のみ**
  - **セル内に `|` を書かない**
  - **種別・優先度・状態を詳細節に書かない**。一覧が正
  - 詳細節の項目は `背景`（必須）に続けて `対応方針` / `着手条件` / `優先度の根拠` / `関連` を必要なだけ
  - 詳細節の並び順は一覧と同じにする
- **完了になったエントリは、状態更新と同じコミットで[closed_23_技術改善バックログ.md](./closed_23_技術改善バックログ.md)へ移す**（本書には未着手・進行中・保留だけを残す）。**一覧の行と詳細節はセットで移す**——`sh scripts/ledger-move.sh T-XX` が両方を移す
- 判断の経緯は本文に書かず、`log_23_技術改善バックログ.md` へ日付順に積む（最初のエントリが出た時点で作る）

### 種別

| 種別 | 何に触るか | 着手時に何が網になるか |
|---|---|---|
| 内部設計 | 本番コード（`androidApp/src/main`・`shared/*/src/main`）の構造（挙動不変） | 既存テスト。**変異させて振る舞い保存を確かめる** |
| テスト | テストコードのみ（本番コード不変） | 本番コードに触れないので回帰の心配がない |
| ツール整備 | `scripts` / CI / `.claude` / 開発環境 | **自動テストの網が無い**。実行して確かめる |
| 依存追随 | 依存ライブラリ・Gradle・AGP の更新 | 上流待ちが多く自分では動かせない。**再確認の契機を必ず書く** |
| 調査 | 何も変えない。判断を記録する | 成果物は決定そのもの |

## 詳細

### T-11

- 背景: `instrumented` ジョブは毎回 Android Emulator（約 300MB）と aosp-atd のシステムイメージ（約 500MB）をダウンロードしている。`actions/cache` でイメージのディレクトリだけを復元すると、GMD が emulator の導入をスキップして `pixel6Api35Setup` が失敗した（main の run 33232649012）
- 対応方針: キャッシュするなら `$ANDROID_HOME/emulator` と `system-images/android-35/aosp_atd/x86_64` の両方を、emulator のバージョンをキーに含めて復元する。効果（短縮時間）を計測してから採否を決める
- 着手条件: instrumented ジョブの所要時間が気になり始めたら。public 化後は実行時間が無制限なので急がない
- 関連: [開発基盤検討](../検討/31_開発基盤検討.md) §8

### T-12

- 背景: `ci.yml` の Action は major タグ固定（`@v7` 等）。現状はトークンが `contents: read` でシークレット参照も無く、Dependabot が追随するので妥当な水準
- 対応方針: ⑤ で署名鍵を CI に持ち込む段階で、各 Action をコミット SHA に固定する（Dependabot はコメントのバージョン表記を頼りに SHA も更新できる）
- 着手条件: CI にシークレットを入れるとき
- 関連: [開発基盤検討](../検討/31_開発基盤検討.md) §8

### T-17

- 背景: `RoomMigrationTest` は assert が 0 件・`ALL_MIGRATIONS` が空・`runMigrationsAndValidate` 未使用で、実質「現行バージョンの DB が開ける」ことだけを見る煙テスト。T-24 で `version = 2` に上げたが Migration を書かなかったため、検証対象の遷移がまだ 1 本も無い
- 対応方針: `runMigrationsAndValidate` へ切り替え、`ALL_MIGRATIONS` に追加した `Migration` を登録する
- 着手条件: 最初の `Migration` を書くとき（＝公開後にスキーマを変えるとき。CLAUDE.md「スキーマ変更時の手順」と同時に行う）
- 関連: T-13 のレビューで test-reviewer が指摘

### T-21

- 背景: instrumented テストは本物の `ReBuyApplication`（Koin を起動する）の上で走り、DB を差し替えていないため、端末の本番 DB を読み書きする。使い捨てのエミュレータ（GMD）では実害が薄いが、実機で `connectedAndroidTest` を回すとオーナーの実データに依存し、憲章 §10 の姿勢とも噛み合わない。DB を用意できないことが理由で「買い物を終わるとホームへ戻る」「空状態のボタンからアイテム一覧へ遷移する」の 2 経路が自動化できず手動確認に残っている
- 対応方針: `loadKoinModules` で `AppDatabase` の定義を in-memory のものに差し替え、DAO へ直接シードしてから画面を操作する形にする。テスト側で `startKoin` を呼ぶと本物の `Application` と衝突するので、差し替えは `loadKoinModules` / `unloadKoinModules` で行う。そのうえで上記 2 経路を自動化する。あわせて `ViewModelScopeTest` の逆向き（entry が backstack に残っている間は ViewModel が保持されること）も書く——買い物画面の終了確認ダイアログを開くのにチェック済みの品目が要るため、シードできるようになって初めて書ける
- 優先度の根拠: 実機でテストを回した瞬間に実データを触る。手動確認に残っている経路も減らせる
- 補足: `RoomMigrationTest` と `KoinGraphTest` は検証対象が `:shared:data` なのに `:androidApp` の androidTest にある（GMD を 1 本に保つための判断。段 2 の計画を参照）。そのため schemas の assets 指定がモジュール境界をまたぐ。この案件で `:shared:data` 側に androidTest を持たせるかも一緒に判断する
- 関連: T-18 のレビューで test-reviewer が指摘

### T-25

- 背景: T-24 の日時テストはコンバータ単体（純粋関数）で止まっており、DB を越える経路が未検証。押さえられていないのは 3 点。(a) 列の affinity が `INTEGER` であること——`2.json` はビルドのたびに生成し直されるので退行検知にならない、(b) `lastBoughtAt = null` の往復——Room が生成する null 分岐はコンバータの非 null シグネチャでは表現できず、`getString` → `getLong` へ経路が変わった箇所、(c) 旧 v1 の DB を持つ端末が起動時に落ちること——T-24 でオーナーが決めた挙動なのに、誰かが `fallbackToDestructiveMigration()` を足しても全件緑のまま通る
- 対応方針: (a)(b) は in-memory DB で DAO の往復を見る。(c) は `AppDatabase.getDatabase` が DB 名を固定して `INSTANCE` をキャッシュしているため、実データを触らずに production のビルダー設定を通せる形（テスト用に DB 名を差せる口）が要る
- **追加（2026-08-30、T-31 ステップ 8）**: (d) **旧経路で作った DB を新経路で開けること**。本番の DB オープンは「framework SQLite ＋ 相対名」から「`BundledSQLiteDriver` ＋ 絶対パス」へ変わったが、これを通るテストが 1 本も無い。手動のアップグレードインストールでしか確かめていない。データ消失という最悪の失敗モードに対して網が無い
- 着手条件: T-21 で in-memory DB への差し替えを入れるとき。同じ足場を使う
- 優先度の根拠: (c) はデータが黙って消える方向への退行を素通しする。ただし ⑤ までは守るべき実データが無いので急がない
- 関連: T-24 のレビューで test-reviewer が指摘

### T-27

- 背景: `HomeViewModel.RIPPLE_DELAY_MS`（200ms）と `ShoppingViewModel.FINISH_SHOPPING_DELAY_MS`（500ms）は、波紋が出切る前に行が動かないように・スピナーが一瞬で消えないようにという **UI の見せ方の都合**が ViewModel に降りてきたもの。T-26 でこの遅延を「守るべき挙動」としてテストに固定したため、正しい置き場所へ動かすと網が赤くなる
- 対応方針: 遅延を Composable 側（クリックハンドラ）へ移す。移した先で待っている間に画面を離れると更新が落ちうるので、どのスコープで待つかを決めてから動かす
- 優先度の根拠: 現状で困っていない。③ の段 3 で UI を `:shared:ui` へ移すときに一緒に片づけるのが自然
- 関連: T-26 のレビューで code-quality-reviewer が指摘

### T-30

- 背景: `main` にブランチ保護が無く、必須チェックも設定していない。そのため CI が pending のままでもマージできる。実際に T-29 で `gh pr merge --auto` を使ったところ、必須チェックが未設定のリポジトリでは auto-merge が成立せず即マージにフォールバックし、`build` と `instrumented` が走り切る前にマージされた（結果は緑だったが、それは結果論）。いまは「オーナーの合図」と「AI が CI を見る」という運用だけが守っている
- 対応方針: `main` にブランチ保護を設定し、`docs` / `build` / `instrumented` を必須チェックにする。これで `gh pr merge --auto` が意図どおり働き、pending のままマージすることが構造的にできなくなる。**直コミットを塞ぐかは別問題**——[git 運用定義書](../仕様/16_git運用定義書.md) は docs と軽微な変更の `main` 直コミットを認めているので、その運用を壊さない設定にする（`Require a pull request before merging` は入れない、または管理者を除外する）
- 優先度の根拠: 機械で守れることを運用で守っている。一人開発なので事故の頻度は低いが、`--auto` の挙動のように「守っているつもり」になる形が最も危ない
- 関連: T-29 のマージで実際に踏んだ。[git 運用定義書](../仕様/16_git運用定義書.md) §1.1 のリスク別ルーティング

### T-31

- 背景: `:shared:*` の 3 モジュールはまだ `com.android.library` で、コードは Android 専用のまま。③ の目的（iOS へ到達する）にはここを KMP 化して `commonMain` へ移す必要がある
- 対応方針: [段 3 実装計画](./plan_23_kmp段3実装計画.md)。各モジュールで「KMP 化」と「`commonMain` への移送」を別のコミットに分ける——前者は同じコードが同じターゲットでコンパイルされるだけなので Android の挙動が構造的に変わりようがなく、壊れたときに原因が Gradle の構成かコードの移送かに必ず切り分かる。iOS はスタブと全画面の 2 回出す
- 着手条件: T-28a（build-logic の立ち上げ）が済んでいること。実際には計画のステップ 1 がそれにあたる
- 優先度の根拠: ③ の本体。段 4（iOS シェル）の前提
- 関連: [KMP 化検討](../検討/32_KMP化検討.md) §3〜§9・§11・§13。T-28a / T-28b を内包する

### T-32

- 背景: KMP ライブラリプラグインはホストテストが既定で無効で、開け忘れると件数が 0 のままビルドが緑になる。段 3 のステップ 5 では、3 モジュールが KMP になったことで `./gradlew testDebugUnitTest` が一致するモジュールを失い、**0 件で緑**になった（入口を `testAndroidHostTest` へ移して対処済み）。いま 122 件を守っているのは「人が数えている」ことだけで、[段 3 実装計画](./plan_23_kmp段3実装計画.md)の残りステップは source set の付け外しが最も多い区間に入る
- 対応方針: ホストテストの source set を持つモジュールで実行件数が 0 なら落とす検査を `rebuy.android.base` に置く。**モジュールごとの期待件数は書かない**——書くと今度はその数字の更新漏れが起きる。`src/androidHostTest` があるのに 0 件、という条件なら `:shared:domain`（テストを持たない）を自動的に除外できる。`afterSuite` は設定キャッシュで使えないので、結果 XML を読む形になる
- 着手条件: 段 3 の**ステップ 13 の前**。ステップ 13 の後は `androidHostTest` が `KoinModulesTest` 1 件だけになり、`commonTest` が 0 件になっても両タスクが緑で通ってしまう（T-31 のステップ 10 のレビューで test-reviewer が指摘）。それ以前に入れると移送中の一時的な 0 件で作業が止まるので、ちょうどこの位置
- 優先度の根拠: 段 3 で 2 回踏んだ形の事故を機械で止める。ただし段 3 の間は人が件数を数える運用が続くので急がない
- 関連: T-31 のステップ 5 のレビューで test-reviewer が指摘

### T-33

- 背景: convention plugin が `rebuy.android.base`（application / library / KMP の 3 系統を `withId` で振り分ける）と `rebuy.kmp.ios`（iOS ターゲット）の 2 つに分かれている。前者は自分のファイル冒頭で「各モジュールの **Android** の土台」と宣言しているのに `:shared:*` の KMP 設定も抱えており、名前と役割がずれている。モジュール側は 2 つの id を書く必要があり、書き忘れの余地も残る
- 対応方針: 分ける軸を「プラットフォーム」から「**モジュールの原型**」に変える。`rebuy.kmp.library`（KMP の android ターゲット設定 ＋ iOS ターゲット）と `rebuy.android.app` の 2 つにすると、モジュール側の id が 1 つになり、名前と役割も一致する
- 着手条件: 段 3 が終わって `:shared:*` の形が固まってから。段 3 の途中は source set の付け外しが続くので、土台を動かすと切り分けが難しくなる
- 優先度の根拠: いまの形でも動く。読みやすさと書き忘れの余地の話なので急がない
- 関連: T-31 のステップ 6 のレビューで code-quality-reviewer が提案

### T-34

- 背景: 本番の DB オープンは T-31 ステップ 8 で `BundledSQLiteDriver` ＋ 絶対パスになったが、`RoomMigrationTest` は旧オーバーロード `Room.databaseBuilder(context, klass, name)` ＋ `openHelper` のままで、**framework SQLite の経路を開いている**。緑なのは「壊れなかった」からではなく「本番と違うものを見ている」から。⑤ で `Migration` を書き始めたとき、本番と違う経路で検証したことになる
- 対応方針: `MigrationTestHelper` の driver ベースのコンストラクタへ寄せ、`openHelper.writableDatabase.close()` を `db.close()` にする
- 着手条件: 最初の `Migration` を書くとき（T-17 と同時）。それまでは検証対象の遷移が 1 本も無い
- 優先度の根拠: いま緑なので急がないが、緑の意味が本来と違う
- 関連: T-31 のステップ 8 のレビューで test-reviewer と code-quality-reviewer が指摘

### T-35

- 背景: iOS で走るテストは Converter の純粋関数だけで、`AppDatabaseConstructor` の `actual` が KSP で生成されているか、`BundledSQLiteDriver` と Documents パスの配線が通るかは**シミュレータで起動するまで分からない**。CLAUDE.md の「Koin は依存グラフをコンパイル時に検証しない」から `KoinModulesTest` / `KoinGraphTest` を置いた理屈が、iOS 側では丸ごと抜けている
- 対応方針: `shared/data/src/iosTest` に 1 件。`Room.inMemoryDatabaseBuilder<AppDatabase>()`（native にはある。common には無いので `commonTest` には置けない）＋ `BundledSQLiteDriver` で DB を組み、`insertItem` → `getAllItems().first()` の往復を見る。生成 `actual`・driver・`TypeConverters` が本物の SQLite を通ることまで一度に固定できる
- 着手条件: **ステップ 15 の前という当初の条件は満たさずに進んだ**（経緯は log_23）。いつでも着手できる
- 優先度の根拠: 段 3 を通して iOS 側は手動確認しか無い。ステップ 15 でシミュレータの往復（カテゴリー追加・削除）が通ることは人の目で見たが、**それを繰り返せる形にはなっていない**
- 関連: T-31 のステップ 8 のレビューで test-reviewer が指摘。iOS の網という意味では [T-42](#t-42) と地続き

### T-36

### T-37

- 背景: Compose Resources の書式化は `String.format` ではなく `%(\d+)\$[ds]` の正規表現置換で、**解釈できない書式（`%s`・`%.2f`・`%%`）は例外を出さずに生のまま画面へ出る**。いま `strings.xml` にあるのは `%1$s` 3 件だけで、うち 3 件とも `StringResourceFormatTest` が期待値リテラルで固定している。**新しく足した文言は誰も見ていない**
- 対応方針: `strings.xml` に対する静的検査（`scripts/docs-check.sh` と同じ形の 1 スクリプト）で、`%` が `%N$s` / `%N$d` 以外の形で現れることを禁じる。文言を足すたびに固定テストを増やすより広く効き、維持費がほぼゼロ
- 着手条件: T-31 のステップ 16（CI のジョブを組み直すとき）。検査を足しても CI から呼ばなければ意味が無いので、CI に触る回に一緒に入れる
- 関連: T-31 のステップ 11 のレビューで test-reviewer が提案

### T-38

- 背景: `TextFieldAddDialog` と `TextFieldEditDialog` は初期値・`onConfirm` の引数・ボタン文言 2 件しか違わない。加えて `TextFieldEditDialog` は `remember { mutableStateOf("") }` ＋ `SideEffect { inputString = editName }` という書き方をしている。**いまは壊れていない**——`SideEffect` は関数本体のスコープにあり、入力で再コンポーズされるのは `inputString` を読んでいる内側のラムダだけなので `SideEffect` は再実行されない（実機で入力できることを確認済み）。ただし composable の構造に依存した危うい形で、`remember(editName) { mutableStateOf(editName) }` なら構造に依らず正しい
- 対応方針: `SideEffect` を落として `remember(key)` にする。そのうえで 2 つのダイアログを 1 つに畳めるかを見る。どちらも表示と挙動は変えない
- 着手条件: T-31 のステップ 13 の後。ダイアログは `commonMain` へ移送済みだが、呼び出し元の画面はステップ 13 で移る。**入力→確定→`onConfirm` の値を見る instrumented テストが 1 本も無い**ので、直す前にそれを置く
- 関連: T-31 のステップ 12 のレビューで code-quality-reviewer が指摘

### T-42

- 背景: Android には GMD の instrumented テストと `adb` のハーネス（`uiautomator dump` ＋ `screencap` の 21 画面走査）があるが、**iOS には画面を触る手段が何も無い**。ステップ 15 では macOS の合成クリック（`CGEvent`）でしのいだが、**人が別のウィンドウを触るとクリックが他のアプリへ飛ぶ**（実際に Chrome へ飛んだ）。誤操作の危険があり、成否も安定しない。**ステップ 15 で見つけた落とし穴 22 のような iOS 固有の不具合は、Android のテストでは 1 件も捕まらない**
- 対応方針: 次の 3 つを比べる。**本命は (c)**——instrumented テストを common へ寄せられれば、Android と iOS の網が 1 本になる
  - (a) `idb`（fb-idb）を入れる。`idb ui tap` がフォーカスに依存せずシミュレータへ直接送るので `adb shell input tap` と同じ形になり、画素比較の走査を iOS でもそのまま回せる。導入は簡単だが CI には載せにくい
  - (b) `iosApp/` に XCUITest ターゲットを足す。`xcodebuild test` で CI に載る正攻法だが、テストを Swift で二重に書くことになる
  - (c) Compose Multiplatform の `runComposeUiTest` を `commonTest` に置く。UI 階層ではなく Compose のセマンティクスを直接叩くので、**`NavigationTest` など既存の instrumented テストを `commonTest` へ移せる可能性がある**。文言を `Res.string.*` から引けるので、既存の方針をそのまま延長できる
  - (d) Maestro。YAML の flow 1 本が Android と iOS の両方で回り、Swift も Kotlin も書かない。**ただし iOS ではネイティブのアクセシビリティツリーを見るので、1 枚の `UIView` に描く Compose の階層が見えるかが分かれ目**（Maestro 側に issue #1549 がある。CMP 1.8.0 で同期が遅延化され `testTag` が `accessibilityIdentifier` に対応づくとされており、本リポジトリの 1.12.0 では直っている可能性が高いが**未実測**）。採るなら **`testTag` で選び `testTag` で assert する**——YAML から `Res.string.*` は引けないので、文言で assert すると「文言を変えたらテストが古い値を主張する」状態に戻る
- 分担の見立て: **(c) と、(b)/(d) は競合ではない。** `NavigationStateRestorationTest`（プロセス death からの復元）と `LicenseLibrariesTest`（資産が APK に入っているか）は実物を起動しないと見られないので、厚みを (c) に置き、実物を起動する薄い層を (b) か (d) で持つ形になる
- 着手条件: T-31 のステップ 16（CI に macOS の `ios` ジョブを足す）と同時に決める。ジョブの中身が案ごとに変わる。**決める前に Maestro を 10 分だけ実測する**——アクセシビリティ階層が見えるかどうかで (d) が候補から落ちる
- 優先度の根拠: **iOS の網がゼロのまま段 4 へ進むと、iOS だけで壊れる変更が誰にも止められない**。落とし穴 22 は人が偶然踏んで見つけた
- 関連: T-31 のステップ 15。[T-35](#t-35)（iOS の DB と DI のスモークテスト）とあわせて考える
