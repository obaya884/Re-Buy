# 技術改善バックログ

- 作成日: 2026-08-29
- 目的: 技術負債の返済・リファクタリング・開発ツール整備など、**プロダクト挙動を変えない技術活動**を、要求（F-XXX / N-XX）とは別軸で管理・計画する
- 関連文書: [開発基盤検討](../検討/31_開発基盤検討.md) ／ [要件バックログ](./22_要件バックログ.md)（プロダクト軸の台帳）

## この文書の守備範囲

プロダクトの**挙動**に関わる変更は扱わない。ここに書くのは、ユーザーから見た挙動を変えずに**開発の健全性を上げる活動**——依存追随・CI/ツール整備・内部設計の改善・テスト補強・調査など。

- 採番は **T-XX**。1 系列で通し、種別で区別する
- 種別: **何に触るか＝着手時に何が網になるか**で分ける（下表）
- 優先度: `高` / `中` / `低` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`
- **1 エントリ＝[一覧](#一覧)の 1 行＋[詳細](#詳細)の 1 節**。一覧は索引に徹し `ID / タイトル / 種別 / 優先度 / 状態 / 詳細` の 6 列を持つ
  - **見出しは `### T-XX` の ID のみ**
  - **セル内に `|` を書かない**
  - **種別・優先度・状態を詳細節に書かない**。一覧が正
  - 詳細節の項目は `背景`（必須）に続けて `対応方針` / `着手条件` / `優先度の根拠` / `関連` を必要なだけ
  - 詳細節の並び順は一覧と同じにする
- **完了になったエントリは、状態更新と同じコミットで[closed_23_技術改善バックログ.md](./closed_23_技術改善バックログ.md)へ移す**（本書には未着手・進行中・保留だけを残す）。**一覧の行と詳細節はセットで移す**——`sh scripts/ledger-move.sh T-XX` が両方を移す
- 判断の経緯は本文に書かず、`log_23_技術改善バックログ.md` へ日付順に積む（最初のエントリが出た時点で作る）

### 種別

| 種別 | 何に触るか | 着手時に何が網になるか |
|---|---|---|
| 内部設計 | `app/src/main` の構造（挙動不変） | 既存テスト。**変異させて振る舞い保存を確かめる** |
| テスト | テストコードのみ（本番コード不変） | 本番コードに触れないので回帰の心配がない |
| ツール整備 | `scripts` / CI / `.claude` / 開発環境 | **自動テストの網が無い**。実行して確かめる |
| 依存追随 | 依存ライブラリ・Gradle・AGP の更新 | 上流待ちが多く自分では動かせない。**再確認の契機を必ず書く** |
| 調査 | 何も変えない。判断を記録する | 成果物は決定そのもの |

## 詳細

### T-11

- 背景: `instrumented` ジョブは毎回 Android Emulator（約 300MB）と aosp-atd のシステムイメージ（約 500MB）をダウンロードしている。`actions/cache` でイメージのディレクトリだけを復元すると、GMD が emulator の導入をスキップして `pixel6Api35Setup` が失敗した（main の run 33232649012）
- 対応方針: キャッシュするなら `$ANDROID_HOME/emulator` と `system-images/android-35/aosp_atd/x86_64` の両方を、emulator のバージョンをキーに含めて復元する。効果（短縮時間）を計測してから採否を決める
- 着手条件: instrumented ジョブの所要時間が気になり始めたら。public 化後は実行時間が無制限なので急がない
- 関連: [開発基盤検討](../検討/31_開発基盤検討.md) §8

### T-12

- 背景: `ci.yml` の Action は major タグ固定（`@v7` 等）。現状はトークンが `contents: read` でシークレット参照も無く、Dependabot が追随するので妥当な水準
- 対応方針: ⑤ で署名鍵を CI に持ち込む段階で、各 Action をコミット SHA に固定する（Dependabot はコメントのバージョン表記を頼りに SHA も更新できる）
- 着手条件: CI にシークレットを入れるとき
- 関連: [開発基盤検討](../検討/31_開発基盤検討.md) §8

### T-14

- 背景: `InstantDateFormatStringConverterTest` は書き出し方向（`toString`）だけを正常 2 件・例外 2 件で押さえており、読み出し方向（`toInstant`）は正常 2 件のみで異常系が 0 件。Room が DB から読むのはこちらの向きで、非準拠文字列が通る経路が未検証。さらにテスト入力の `OffsetDateTime` が全件 UTC 由来のため、実装の `withZone(ZoneOffset.UTC)` を `ZoneId.systemDefault()` に変えても TZ=UTC の CI では緑のまま通り、「UTC 文字列として保存する」条項がどのテストにも固定されていない
- 対応方針: `toInstant` に空文字・時刻部欠落・末尾余剰・ゼロ埋めなし・月が範囲外・4 桁年の範囲外を足す。非 UTC オフセット由来の `Instant` を 1 件入れて UTC 変換を固定する。往復（`toInstant(toString(x)) == x`）も 1 件
- 優先度の根拠: 条項が守られていない箇所があり、実装を壊してもテストが気づかない
- 関連: T-13 のレビューで test-reviewer が指摘。CLAUDE.md「アーキテクチャ / データ層」

### T-15

- 背景: `ItemStatusConverter` にテストが 1 件も無い。CLAUDE.md は「enum の `value` は既存 DB と互換を壊さない限り変更しない」と定めているが、この条項を守るテストが存在しない
- 対応方針: `NO_DEAL→0` / `IN_SHOPPING_LIST→1` / `CHECKED_IN_SHOPPING_LIST→2` の対応と、未知の値を渡したときの挙動を固定する
- 優先度の根拠: 値がずれると既存 DB のデータが別の状態として読まれる。壊れ方が静か
- 関連: T-13 のレビューで test-reviewer が指摘

### T-16

- 背景: `InstantDateFormatStringConverterTest` は `.let {}.also {}` のチェーンで書かれており、実測値が `it` に隠れて期待値との区別が目で付かない（T-13 の引数順ミスが生まれた素地）。加えて 1 つの `@Test` に 4 ケースを直列に詰めているため最初の失敗で残りが走らず、例外系の `assertTrue(... is DateTimeException)` は失敗時に真偽しか出ない。テストメソッド名と KDoc の有無も 2 つの `@Test` で揃っていない
- 対応方針: 実測値に名前を付ける素直な形へ直し、ケースごとに `@Test` を分け、例外系は `assertThrows` にする
- 関連: T-13 のレビューで code-quality-reviewer と test-reviewer が指摘

### T-17

- 背景: `RoomMigrationTest` は assert が 0 件・`ALL_MIGRATIONS` が空・`runMigrationsAndValidate` 未使用で、実質「v1 の DB が開ける」ことだけを見る煙テスト。`version = 1` の現状では妥当だが、このままではスキーマ検証が効かない
- 対応方針: `runMigrationsAndValidate` へ切り替え、`ALL_MIGRATIONS` に追加した `Migration` を登録する
- 着手条件: `AppDatabase` の `version` を 2 に上げるとき（CLAUDE.md「スキーマ変更時の手順」と同時に行う）
- 関連: T-13 のレビューで test-reviewer が指摘
